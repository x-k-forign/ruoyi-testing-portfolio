## 2. 请求解读

### 浏览器请求

```text
GET http://127.0.0.1:5173/dev-api/system/user/list?pageNum=1&pageSize=10&userName=t25_a_query
```

### Postman 请求

```text
GET http://127.0.0.1:8080/system/user/list?pageNum=1&pageSize=10&userName=t25_a_query
```

| 内容 | 解释与实际设置 |
|---|---|
| http | 协议 |
| 127.0.0.1 | 本机地址 |
| 5173 / 8080 | 前端代理端口 / 后端端口 |
| /dev-api | 前端代理前缀，代理转发时移除；直连后端不添加 |
| /system/user/list | 业务接口路径，不是页面资源 |
| GET | 查询用户列表 |
| pageNum=1 | 第1页 |
| pageSize=10 | 每页10条 |
| userName=t25_a_query | 按账号名筛选；实现为模糊匹配，本次同时精确核对返回账号 |
| Authorization | 必要认证头，格式为 `Bearer <REDACTED>`；Postman Bearer Token 输入框只填凭证本身 |
| Body | 本GET按指导设置none；提交截图未展开Body，未独立导出核查，不伪造可见证据 |
| Content-Type: application/json | 浏览器截图中该字段属于响应头，说明响应格式；它不是查询参数 |

本次用户曾将 application/json 记为查询参数，已在指导中纠正。用户还曾在 `/getInfo` 的 URL 输入框中带上 GET，已指导删除；其随后返回业务200和admin身份。这些是学习操作修正，不登记产品缺陷，不计为额外通过用例。

URL查询参数传输时是文本；服务端将 pageNum/pageSize 绑定为数字。响应中的 code、total、userId、deptId 是 JSON 数字；status="0" 是字符串，admin=false 是布尔值，null 是空值，rows/roles 是数组，dept/user 是对象。用户粘贴文本中的 Markdown `**` 和转义反斜杠不属于原始JSON；归档摘要使用合法JSON并明确为节选。

### 认证来源与必要头

前置登录练习已实际返回顶层token；前端请求封装将凭证放进 Authorization。用户本次从浏览器用户列表请求取得凭证，在 Postman 的 Bearer Token 位置使用，随后 `/getInfo` 确认 userName=admin、userId=1。

不用复制全部浏览器头：Cookie、Authorization 的真实值是敏感信息；Sec-CH-UA、Sec-Fetch-*、User-Agent、Referer等通常不属于本接口业务输入；Host、Content-Length由工具生成。isToken、repeatSubmit是前端封装控制项，不能当必需业务头照抄。本接口复现以有效认证和相同查询参数为核心。

## 5. AI辅助场景说明

按本次授权由AI作答，仅作为交付说明，不作为用户独立能力证明。

**同样是200响应，为什么可能一个业务成功、另一个失败？**

HTTP200和JSON业务code不是同一层。若依可能用HTTP200返回正文code=403或500，表示业务被拒绝或失败。本次还核对code=200、目标账号/编号、部门及查询条件一致，才判断该查询复现场景通过；未来写操作还需核对实际持久化变化。

**把浏览器全部请求头复制到接口工具，可能保留哪些不必要或敏感信息？**

可能复制真实token、Cookie及记住密码相关值，还可能带入浏览器环境专用头或过期凭证。Postman仅设置本接口所需认证和参数；JSON正文接口才按需要设置Content-Type。浏览器身份和查询对象必须区分，不能用被查账号名证明操作者身份。
