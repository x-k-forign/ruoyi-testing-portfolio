## 2. 规则和字段核对

| 核对点 | 结论与处理 |
|---|---|
| 创建字段 | userName、nickName、password为字符串；deptId为整数，roleIds为整数数组；正文JSON，不混同查询参数 |
| 账号长度 | 页面2～20位，实体非空且最多30位；正常链使用2～20位，差异已在文档保留 |
| 昵称 | 页面必填；实体最多30位，缺少同等非空校验；不将两者说成一致 |
| 密码 | 项目规则6～20位；后端登录5～20位、新增实体无同等长度注解；沿用BUG-T3-002，不放宽预期 |
| 空值和关联 | 缺失、null、空字符串、空数组分别设计；正常链使用明确有效关联。空部门/空角色仍按T3保留观察 |
| 角色授权 | PUT /system/user/authRole通过Query传userId、roleIds，非JSON正文；完全清空角色的编码仍待专项核实，本轮正常链不依赖它 |
| 返回结构 | 登录token在顶层；用户列表为rows/total；详情用data及顶层roleIds；新增不保证返回ID |
| 认证与范围拒绝 | 认证入口业务401、权限异常403、范围ServiceException默认500；HTTP与业务code分别记录，明确为源码分支预期而非T4全量实测 |
| 项目与实现差异 | 撤权、调部门即时生效为项目规则；禁用旧会话及增授时效仍待确认；既有缺陷不重复建单 |

OpenAPI只把SysUser.userName列为required，LoginBody没有required清单；实际登录仍执行账号、密码及验证码检查。因此生成文档不替代服务实现与项目规则。

运行观察继续引用[T4.1请求对照](T4.1_请求解读与验收记录.md)：管理员查询和身份补证实际成功。其他Responses中的200/401/403/500是已注明的源码预期，未当作本轮执行结果。

参数类型错误（例如deptId使用非数字字符串）、遗漏必填字段等请求变体放在T4.5执行设计中单独记录，不用一次异常概括所有参数错误；拒绝写操作必须有前后回查。身份、可分配范围和目标存在性在执行前重新核实，不能固定照搬历史编号和数量。

以下是原表未单独覆盖的认证设计场景，名称只是场景标识，不冒充已有TC编号。T4.5形成执行卡时独立编号，不能直接关闭TC-L12-01或增加T3统计。

| 场景标识 | 请求和前置 | 唯一变化 | 预期与取证 |
|---|---|---|---|
| AUTH-NONE | 有效普通账号能查询；GET /system/user/list，固定合法Params | 去除Authorization及认证继承 | 业务401，不返回受保护数据；记录HTTP和正文 |
| AUTH-INVALID | 同上 | 使用本地构造的无效token | 业务401；不得称为自然过期验证 |
| AUTH-LOGOUT | 专用会话A先正常查询并合法退出，独立新会话B作对照 | 以已退出A原token再次查询 | A业务401，B业务200；记录退出和两次查询，结束注销B |

这三项均属于既定“未认证/无效/真实失效凭证”范围，不改变阶段计划。管理员与普通用户分别保管凭证；范围验证按完整分页ID集合比较。

五条直接移交TC-C05-01、TC-C06-01/02、TC-C07-03/04在T4.5执行；TC-C08-01、TC-M07-02、TC-G04-03在T4保留请求及日志证据需求，在T5隔离条件具备后核验事务。故障构造必须有独立源码、库、Redis和恢复方案，不在本次验收中注入故障。

## 4. AI辅助场景说明

**接口文档没有用户新增接口，是否说明功能不存在？**

不说明。可能是分组或扫描范围不同。本次默认分组只有演示接口，未分组OpenAPI实际包含POST /system/user；还可以用页面抓包和用户控制器交叉确认。文档列出接口也不证明已执行成功。

**不存在的角色ID和存在但无权分配的角色ID，为什么分开测？**

前者验证关联对象有效性，后者验证授权边界。用有新增权限的有限身份，分别先确认“确实不存在”和“存在但范围外”，其他参数全部合法；均需回查无新用户或非法关联。两者即使返回相同错误码，也不代表同一个测试点。
