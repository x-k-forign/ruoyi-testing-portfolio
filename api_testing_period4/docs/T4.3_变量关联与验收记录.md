## 3. 失败处理与证据边界

- 初次将响应脚本放在预请求位置，发生pm.response不存在错误；已改为两个执行位置。一次列表请求返回HTTP400的HTML而JSON解析报错，具体根因未完全确认，修正环境变量配置后恢复，不登记产品缺陷。
- 零条匹配后用户曾继续发送详情请求。响应显示未解析的newUserId，而非旧150，证明该次没有沿用旧ID；没有保存失败时环境页的独立截图，不宣称直接看到了变量删除过程。最终环境清理另有截图。
- 本轮是逐条手动发送，执行规则为“上游失败先停止，修正并重跑上游，再发送下游”。一次误发已解释和纠正；没有实测集合Runner自动停止，不声称红色断言能自动阻断请求。后续集合运行需另外设置和验证停止行为。
- 这里的红色“登录成功/唯一匹配”断言，面对故意失败输入时属于预期检查结果；不作为产品新缺陷，也不等同于T4.6“修改断言再恢复”的专项练习已完成。

## 5. AI辅助场景说明

沿用用户此前要求的AI辅助说明方式，不记为用户独立作答。

**本次登录失败，但还留着上次token，会怎样误导结论？** 后续请求可能借旧身份成功，使人误认为本次登录成功。应先清该身份旧token，成功且字段有效才保存，失败停止依赖链；管理员与普通用户分开变量。

**只返回一条记录，为什么还要比较账号名？** 列表是模糊查询，唯一一条也可能不是本批用户。需要同时检查唯一性、精确账号名和ID类型，再把实际ID交给下一请求。查询为空或多条时不能沿用历史ID。
