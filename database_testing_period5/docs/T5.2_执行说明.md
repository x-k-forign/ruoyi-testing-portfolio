## SQL 和接口采用的相同口径

依据 [SysUserMapper.xml](../../sources/backend/ruoyi-system/src/main/resources/mapper/system/SysUserMapper.xml) 的 selectUserList：

- 列表排除 del_flag 不为 0 的用户；status 未指定时，不自动排除停用账号。
- userName 是包含匹配，不是精确等于；本轮前缀只用字母数字，避免下划线、百分号被当成 LIKE 通配符。
- deptId 筛选包含所选部门及其下级部门。202 的下级包含 203，所以“部门树202”不等于“dept_id=202”。
- 普通账号166仅有角色101，data_scope=3，因此另受本部门202范围限制；这是身份范围与请求筛选的交集。
- 本轮显式请求 orderByColumn=userId、isAsc=asc，使用唯一 ID 稳定排序。依据 [PageDomain.java](../../sources/backend/ruoyi-common/src/main/java/com/ruoyi/common/core/page/PageDomain.java) 的参数处理；未假设接口默认顺序稳定。

本轮每页5条。每一页都比较 HTTP 状态、业务码、分页结构、total、按序 ID 和 userName/deptId/status/delFlag 字段；再将全部分页合并，独立核对完整集合、重复、缺失和多余 ID。接口原始响应中无关联系方式等字段不归档，证据只保存上述白名单字段。

## 本轮 SQL 怎么理解

### 精确找到本批用户

```sql
SELECT user_id,user_name,dept_id,status,del_flag
FROM sys_user
WHERE user_name IN ('t521019185631a','t521019185631b')
ORDER BY user_id;
```

准备后返回166和167，均未删除，其中167为停用。清理后这两行仍能查到，但 del_flag 已变为2；没有删除过滤的 SQL 不等同正常列表接口。

### 查本部门和部门树

只查用户自身所属部门202：

```sql
SELECT user_id,user_name,dept_id,status,del_flag
FROM sys_user
WHERE del_flag='0' AND dept_id=202
ORDER BY user_id;
```

本轮准备后为25人。若对应管理员页面部门树筛选，还要包含下级部门：

```sql
SELECT user_id,user_name,dept_id,status,del_flag
FROM sys_user
WHERE del_flag='0'
  AND (dept_id=202 OR dept_id IN
       (SELECT dept_id FROM sys_dept WHERE FIND_IN_SET(202,ancestors)))
ORDER BY user_id;
```

结果为26人，多出的是下级203中的用户105。这是筛选语义差异，不是数据库少数据，也不意味着普通用户166具有下级部门权限。

### 排序和分页

```sql
SELECT user_id,user_name,dept_id,status,del_flag
FROM sys_user
WHERE del_flag='0'
ORDER BY user_id
LIMIT 0,5;
```

`LIMIT 0,5` 跳过0行、取5行，返回本轮第一页 ID：1、2、100、101、103。第二页用 `LIMIT 5,5`，返回104、105、108、109、110。偏移量=(页码−1)×每页条数；它不是起始用户 ID。

完整对照没有只检查前两页：管理员全部用户读取了8页，最后一页1条；普通账号读取5页。逐页和合并后的结果均与 SQL 一致。

### 按部门统计人数

```sql
SELECT dept_id,COUNT(*) AS user_count,COUNT(dept_id) AS non_null_dept_count
FROM sys_user
WHERE del_flag='0'
GROUP BY dept_id
ORDER BY dept_id;
```

| 部门ID | 用户行数 | 非空部门计数 |
|---|---:|---:|
| NULL | 1 | 0 |
| 103 | 1 | 1 |
| 105 | 1 | 1 |
| 200 | 1 | 1 |
| 201 | 2 | 2 |
| 202 | 25 | 25 |
| 203 | 1 | 1 |
| 204 | 3 | 3 |
| 207 | 1 | 1 |

这里一行结果代表一个部门分组；NULL 也形成一组，但不是一个已知部门编号。分组行数合计36，与未删除用户总数相等。

### 按部门和状态分组

```sql
SELECT dept_id,status,COUNT(*) AS user_count
FROM sys_user
WHERE del_flag='0'
GROUP BY dept_id,status
ORDER BY dept_id,status;
```

部门204拆成两组：status=0 有2人，status=1 有1人（本批167）。其余分组见原始 SQL 结果。这个例子说明停用与删除不能混用：167在清理前仍会出现在管理员未加状态条件的列表中。

### 用 HAVING 筛选人数至少为2的部门

```sql
SELECT dept_id,COUNT(*) AS user_count
FROM sys_user
WHERE del_flag='0'
GROUP BY dept_id
HAVING COUNT(*)>=2
ORDER BY user_count DESC,dept_id;
```

本轮结果为202部门25人、204部门3人、201部门2人。WHERE 先排除已删除用户，GROUP BY 再分部门，HAVING 最后排除人数不足2的分组；排序用部门 ID 作为人数相同时的补充条件。

### NULL 与三个 COUNT 的区别

```sql
SELECT COUNT(*) AS user_count,
       COUNT(dept_id) AS known_dept_count,
       COUNT(DISTINCT dept_id) AS distinct_known_departments
FROM sys_user
WHERE del_flag='0';
```

本轮分别为 **36、35、8**：36个未删除用户行，35行有部门编号，涉及8个不同的非空部门。差的1人是既有用户126，其 dept_id=NULL。没有用 IFNULL 把空部门变成0，也没有用 DISTINCT 掩盖多表连接导致的重复。

### 历史逻辑删除

主查询窗口全表70行，其中 del_flag=0 为36行、del_flag=2 为34行；正常列表 total=36 并不表示数据库只存36行。历史151/153仍为逻辑删除，本轮没有恢复或登录这些账号。

## 需要你理解和确认的地方

1. **SQL 和接口必须使用相同口径。** 同一个部门202，精确归属为25人，管理员部门树筛选为26人；必须先明确是否包含下级。
2. **停用不等于删除。** 167停用时仍是未删除行，可被管理员状态筛选查到；清理后 del_flag=2 才被正常列表排除。
3. **COUNT 的对象不同。** 36是用户行数，35是非空部门行数，8是不同的非空部门值数量。
4. **总数一致还不够。** 例如两个列表各有25人，但其中一人不同，仍应判为不一致。本轮实际比较了完整 ID、重复项及必要字段。
5. **管理员基准不等于普通用户权限。** 普通166仅能查本部门202；本批167虽然在数据库中且管理员可见，也不应出现在166的查询结果里。
6. **SQL 结果具有时间条件。** 本轮准备时36人、清理后34人都可以正确，复查要看记录时点和对象状态，不能硬套历史数量。
