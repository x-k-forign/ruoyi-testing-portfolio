## SQL 的执行方式与含义

### 回滚分支

以下是连接A的核心步骤。完整文件在其中穿插连接B的观察，执行时不要跳过：

```sql
START TRANSACTION;

INSERT INTO t5_dml_lab(run_tag,dept_id,role_id,status,note)
VALUES(@r_tag,202,101,'0','draft');
SET @r_id=LAST_INSERT_ID();

-- 写前预览，必须确认恰为本批的一行。
SELECT id,run_tag,dept_id,role_id,status,note
FROM t5_dml_lab WHERE id=@r_id AND run_tag=@r_tag;

UPDATE t5_dml_lab
SET dept_id=204,status='1',note='changed_uncommitted'
WHERE id=@r_id AND run_tag=@r_tag;

SELECT id,run_tag,dept_id,role_id,status,note
FROM t5_dml_lab WHERE id=@r_id AND run_tag=@r_tag;

ROLLBACK;
```

本轮A在回滚前看见ID1已经变为204/1，但B查不到这条未提交的新增记录。回滚后新增和修改一起被撤销。

判断UPDATE成功不能只看“语句执行没有报错”：先确认WHERE匹配了目标行，再核对影响行数和前后字段值。这里每次更新都实际改变了字段值，返回1行；没有用更新同值或0行匹配冒充成功。

### 提交分支

提交分支使用另一个唯一标记和实际ID2，流程同样是插入、预览、修改、查询，最后使用：

```sql
COMMIT;
```

提交后，B在新读取中看到了ID2。本轮还让B执行一次ROLLBACK，再读仍有ID2，说明事务控制只作用于相应连接的当前事务，不能撤销别的连接已经提交的变更。

### 为什么B会看到旧值

本轮按以下顺序真实执行：

```text
B：START TRANSACTION；查询ID2，读到部门204、状态1
A：START TRANSACTION；将ID2改为部门202、状态0；COMMIT
B：继续在原事务查询，仍读到部门204、状态1
B：COMMIT结束原事务；重新查询，读到部门202、状态0
```

在本次REPEATABLE-READ条件下，B的普通SELECT继续使用其事务先前建立的快照；旧结果不能证明A没有提交。本轮使用的是普通一致性读取，没有把这个结论推广到锁定读取或所有DML。[MySQL一致性读取说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)

### 为什么自动提交后不能再回滚

自动提交分支没有执行START TRANSACTION。A插入ID3后，语句已按自动提交方式完成；随后ROLLBACK没有撤销这条记录，B仍查得到。只有后续显式执行针对ID3的DELETE并提交，才完成清理。[MySQL自动提交说明](https://dev.mysql.com/doc/refman/8.4/en/commit.html)

### 建表为什么单独执行

普通CREATE TABLE等DDL会涉及隐式提交，不能把它们夹在本轮DML回滚流程中，再期望普通ROLLBACK恢复整个过程。因此本轮建表单独完成，事务文件中没有CREATE、ALTER、DROP或TRUNCATE，也没有通过切换autocommit来代替事务收尾。[MySQL隐式提交说明](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)

## 需要理解和确认的地方

1. **回滚的边界。** 未提交的事务变更可以撤销，已经提交的数据要通过新的明确操作处理。
2. **连接的边界。** A和B各有自己的事务，B执行ROLLBACK不会撤销A已提交的数据。
3. **读取的时点。** 本轮B读到旧值，是REPEATABLE-READ旧快照的真实表现；要核对连接和事务后再判断是否提交。
4. **自动提交的影响。** 不开启显式事务时，autocommit=1会让本轮INSERT直接提交；显式事务内则要看COMMIT或ROLLBACK。
5. **清理不等于回滚。** 本轮ID2/3已经提交，最终靠精确DELETE再COMMIT清理；保留空表和自增间隙符合预定方案。

自测说明：若A提交后B还看到旧值，先检查数据库目标、连接编号、B是否仍处于旧事务及隔离级别，然后结束旧读取事务再查。API创建用户成功后，SQL窗口ROLLBACK不能证明用户被撤销，因为API使用另一数据库连接并可能已经提交；应通过业务接口及独立数据回查确认。

最后一项是基于事务边界的原理说明，本轮没有新增API调用，不将教学表实验写成若依后端事务已通过。
