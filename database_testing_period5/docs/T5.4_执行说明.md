## 内连接怎样核对有效关联

下面语句对应已执行的inner_user_department_roles，只保留匹配到部门和角色的本批用户：

```sql
SET @target_user_id=168;
SELECT u.user_id,u.user_name,u.dept_id,d.dept_name,
       r.role_id,r.role_key,r.data_scope,r.status AS role_status
FROM sys_user u
INNER JOIN sys_dept d ON u.dept_id=d.dept_id
INNER JOIN sys_user_role ur ON u.user_id=ur.user_id
INNER JOIN sys_role r ON ur.role_id=r.role_id
WHERE u.user_id=@target_user_id
ORDER BY r.role_id;
```

结果有2行，因为请求给168指定了两个角色，不是重复创建了两个用户。不能通过一次大连接的行数判断用户数，先看这一行包含了哪些对象。

角色菜单实际组合为：

| 角色 | 菜单ID | 非空权限 |
|---|---|---|
| 105 | 1、100、1000 | system:user:list、system:user:query |
| 106 | 1、100、1000、1001 | system:user:list、system:user:query、system:user:add |

菜单1是目录，perms为空；它是一条菜单关联，但不增加非空操作权限。两个角色共享菜单1/100/1000，因此7条关联只涉及4个不同菜单和3个不同非空权限字符串。

本轮的统计结果是：user_role_menu_rows=7、users=1、roles=2、menus=4。这里COUNT(DISTINCT u.user_id)用于明确统计不同用户，COUNT(DISTINCT rm.menu_id)用于统计不同菜单；不是把整张查询结果随意DISTINCT后隐藏重复原因。原始7对角色菜单ID完整保留并与创建前基准比较。

## 左连接怎样保留缺失关联

对用户126、127、168查询：

```sql
SELECT u.user_id,u.dept_id,d.dept_id AS matched_dept_id,
       ur.role_id,r.role_id AS matched_role_id
FROM sys_user u
LEFT JOIN sys_dept d ON u.dept_id=d.dept_id
LEFT JOIN sys_user_role ur ON u.user_id=ur.user_id
LEFT JOIN sys_role r ON ur.role_id=r.role_id
WHERE u.user_id IN (168,126,127)
ORDER BY u.user_id,ur.role_id;
```

实际结果摘要：

| user_id | dept_id | matched_dept_id | role_id | matched_role_id |
|---:|---:|---:|---:|---:|
| 126 | NULL | NULL | 101 | 101 |
| 127 | 202 | 202 | NULL | NULL |
| 168 | 202 | 202 | 105 | 105 |
| 168 | 202 | 202 | 106 | 106 |

126是自身dept_id为空，不能叫“引用了一个不存在的部门”；127是没有sys_user_role关联行，不能叫“角色表丢失”。真正的悬空引用需要先看到非空引用ID，再发现对应对象不存在。本轮五类检查均没有发现这种情况。

若把三处LEFT JOIN全部改为INNER JOIN，126在部门连接时被排除，127在角色连接时被排除，最终只剩168的2行。内连接适合核对已有匹配，左连接更适合观察未匹配情况；不能只看内连接没报错就认定关联完整。

## ON 和 WHERE 为什么会改变结果

**状态条件放ON：**

```sql
SELECT u.user_id,ur.role_id,r.role_id AS matched_role_id,r.status
FROM sys_user u
LEFT JOIN sys_user_role ur ON u.user_id=ur.user_id
LEFT JOIN sys_role r ON ur.role_id=r.role_id AND r.status='0'
WHERE u.user_id IN (168,126,127)
ORDER BY u.user_id,ur.role_id;
```

返回4行。127没有角色，但左表用户仍保留，r.role_id和r.status为NULL。

**状态条件移到WHERE：**

```sql
SELECT u.user_id,ur.role_id,r.role_id AS matched_role_id,r.status
FROM sys_user u
LEFT JOIN sys_user_role ur ON u.user_id=ur.user_id
LEFT JOIN sys_role r ON ur.role_id=r.role_id
WHERE u.user_id IN (168,126,127) AND r.status='0'
ORDER BY u.user_id,ur.role_id;
```

返回3行。127的r.status为NULL，无法满足WHERE中的等于0条件，于是整行被过滤。这里没有停用角色样本，实测结论是对“无关联右表”的影响，不冒称已经执行所有角色停用组合。

## 需要理解和确认的要点

1. **一行代表什么。** 一个用户可有两个角色；角色与菜单展开后有7行，并不意味着有7个用户。
2. **NULL要结合来源判断。** 126是未设置部门，127是没有角色关联，105没有自定义范围关联则符合其本部门范围配置；不能看到NULL就一律报错。
3. **ON与WHERE的位置有影响。** 本例把角色状态过滤放WHERE，排除了无角色用户127；找缺失关系时尤其容易漏查。
4. **关联存在与接口授权是两层证据。** 数据库先核对部门、角色、岗位和菜单集合，再用168的新会话核验实际身份和查询范围；没有据此宣称旧会话问题已修复。
5. **去重必须有业务目的。** 统计不同用户或菜单可以按对应ID去重；关联明细仍须保留各角色对应的菜单组合，不能用DISTINCT掩盖错误连接。
