## 三份SQL如何协作

### prepare.sql 准备前置条件

在客户端连接到隔离库并绑定本轮参数后，执行环境、冲突、部门、角色、岗位和权限查询。执行器要求：

- DATABASE()必须为ruoyi_t3_fault_lab。
- run_tag必须是8—20位字母数字，不含LIKE通配符；本轮同时将它作为用户名和remark标记。
- 所有状态的同名用户行必须为0，逻辑删除历史也不能复用为新批次。
- 部门、角色、岗位均存在且正常，角色范围与本轮预期一致。

首次准备和真正发创建请求前各检查一次。前置不符立即停止，不采用REPLACE、忽略重复错误或覆盖旧对象来继续。

```sql
SELECT IF(DATABASE()='ruoyi_t3_fault_lab',1,0) AS database_ok,
       IF(@run_tag REGEXP '^[A-Za-z0-9]{8,20}$',1,0) AS tag_ok,
       (SELECT COUNT(*) FROM sys_user WHERE user_name=@run_tag) AS existing_name_rows;
```

SQL只返回事实；**停止执行的判断由自动化执行器负责**。手工运行时也应先确认返回1、1、0，再发创建请求。打开SQL文件并不等于已经连接正确目标，更不等于前置已通过。

前置通过后复用T4合法新增字段模板，通过接口提交本批用户名、部门200、角色[100]、岗位[1]和本地生成的合规口令。创建后按唯一用户名查询并精确匹配，取得真实ID；不把107、108写死为下一轮ID。

### verify.sql 核对持久化和业务结果

用实际ID、精确用户名和remark三者共同定位：

```sql
SELECT user_id,user_name,dept_id,status,del_flag,remark
FROM sys_user
WHERE user_id=@target_user_id AND user_name=@run_tag AND remark=@run_tag;
```

随后分别核对用户角色、用户岗位及关联对象的状态，避免大连接的重复行影响判断。普通身份的预期列表按实际所属部门及del_flag=0构造，再与接口完整分页结果比较。

Postman集合复用T4的GET定义，参数放本轮私有环境；每轮核对管理员身份、当前普通账号身份、两种身份查询用户详情，以及普通用户列表。列表脚本支持继续翻页直到末页，并比较按序ID和完整集合；本批每轮只有1个范围内有效用户，因此实际只需1页，没有冒称本轮验证了多页表现。

### cleanup.sql 精确定位与清理后复查

自动化执行器在删除前、删除后各执行一次同一文件。删除前必须确认目标是本轮真实ID、精确用户名和remark，且不属于该轮原始基线；预览恰为1行、del_flag=0、关联符合本轮记录，才调用删除接口。

```sql
SELECT user_id,user_name,dept_id,status,del_flag,remark
FROM sys_user
WHERE user_id=@target_user_id AND user_name=@run_tag AND remark=@run_tag;
```

执行正常删除接口后，再查到该行del_flag=2、角色与岗位计数为0、未删除本批用户数为0，才判清理完成。若已经处于这种完整清理状态，跳过重复删除；若归属、数量或关联状态异常，先停止调查，不能扩大WHERE条件。

本次三个文件只包含只读业务查询和读取事务的开启/结束。实际创建、删除是后端连接提交的，SQL窗口中的ROLLBACK只结束当前读取事务，不能替代业务清理。

## 需要理解和确认

1. **可重复执行需要新批次。** 本轮107和108使用同一套流程，但标记、ID和会话不同，第二轮不依赖第一轮有效账号。
2. **准备检查和清理检查都有停止条件。** 同名历史记录或归属不符应停止，不能忽略错误继续写入。
3. **清理范围必须精确。** 实际ID、精确用户名、批次备注与原基线共同确认归属，不能只按模糊前缀删除。
4. **逻辑删除与物理归零不同。** 保留两行历史和审计符合本计划，关键是未删除样本为0、关联为空、原基线不受影响。
5. **中断恢复应从实际状态继续。** 第一轮修复后从CLI续跑，没有盲目重发创建请求。
