# T3.2 专项设计方案

2026-10-10。以下是可执行的准备、观察和恢复设计，本次未实施配置变更、密码重置或故障注入。用例继续保留原编号，特殊对象未准备好时仅阻塞对应执行批次。

## 五位密码登录

对应：TC-L09-05，E01/E19、Q02、RK12。创建及页面重置为6—20位；后端登录为5—20位，不能把两个入口合并。

| 步骤 | 操作与检查 |
|---|---|
| 基线 | U5复用账号110：t3_pwd5_1010、部门202、角色101、正常。用户已完成初始合规密码登录及查询。本次保持原密码 |
| 执行准入 | 到该专项时，确认用户同意该专用账号临时改为5位；使用独立admin会话，回查目标110及账号名，其他账号不变 |
| 准备 | 通过管理员身份的PUT /system/user/resetPwd，仅提交userId=110和本地保管的5位测试密码。需要system:user:resetPwd及目标范围权限。新密码由用户本地输入，不入共享证据 |
| 准备结果 | 分开记录HTTP状态及业务code；响应成功只是准备证据，不能判登录通过。若入口拒绝，记录真实响应，不改数据库、不绕过鉴权；该执行记录为阻塞 |
| 验证 | 新的独立会话使用该账号、正确5位密码和新有效验证码执行POST /login；确认账号未锁定、来源获准。核对返回认证结果，再获准查询核对userId=110 |
| 正常对照 | 结束5位观察后，用正常页面重置为满足字符规则的6位密码，独立新登录作6位相邻对照；两个取值分别记结果 |
| 恢复 | 通过正常页面恢复用户保管的合规密码；退出本轮测试会话，新登录回查账号、角色和代表查询。保留110，不删除现有学习成果 |

前端请求前缀为/dev-api，直接请求后端时不带该前缀。源码依据：SysUserController.resetPwd（约192—201行）在权限/目标范围检查后加密保存；所读入口没有页面相同的长度校验。此为准备可行性依据，不是后端已实测可接收的证明。执行时不在普通新增/重置页面反复尝试5位。

Q02继续保留“创建与登录密码限制是否应统一”。即使5位认证成功，也只记实现观察，不自动判业务要求满足。

## 事务内故障与回滚

对应：TC-C08-01、TC-M07-02、TC-G04-03，E07/E17、RK08/RK11。实际故障与SQL补证按原计划放在T4/T5，本阶段把触发、证据及恢复方案设计清楚。

### 隔离与准入

- 使用后端固定提交的单独源码副本，HTTP端口18080，数据库ruoyi_t3_fault_lab，独立Redis实例及上传/日志目录。新库由后续受控准备建立；不能把初始化SQL指向ruoyi_t2_lab。
- 管理身份和测试组织在隔离副本中核对实际编号，不能直接套用原库的110/202/101。故障账号分别用t3_fault_new、t3_fault_edit，执行前确认只用于本轮。
- 记录基线提交、补丁、构建产物和实际连接目标。无隔离副本、事务未生效或故障点未构建时，不发故障请求。

### 明确触发点

文件：SysUserServiceImpl.java。仅在隔离副本采用下列受测试开关和唯一用户名双重限制的补丁，不修改正在运行的原源码。

```java
// 辅助方法仅用于隔离副本；不捕获抛出的异常。
private void failForT3(String point, SysUser user) {
    if (point.equals(System.getProperty("t3.fault.point"))
            && user.getUserName().equals(System.getProperty("t3.fault.user"))) {
        boolean active = org.springframework.transaction.support
                .TransactionSynchronizationManager.isActualTransactionActive();
        throw new IllegalStateException("T3_FAULT:" + point
                + ":txActive=" + active + ":userId=" + user.getUserId());
    }
}
```

| 场景 | 插入位置与开关 | 请求 |
|---|---|---|
| C08创建回滚 | insertUser已执行userMapper.insertUser、insertUserPost和insertUserRole之后，在return rows之前调用failForT3("insert-after-all", user)。启动属性t3.fault.point=insert-after-all、t3.fault.user=t3_fault_new | 有权限的管理身份POST /system/user；合法唯一名、非空合法角色数组，岗位如纳入则选合法岗位 |
| M07修改回滚 | updateUser末尾改成int rows=userMapper.updateUser(user); failForT3("update-after-all", user); return rows;。启动属性t3.fault.point=update-after-all、t3.fault.user=t3_fault_edit | 有权限的管理身份PUT /system/user；提交完整合法编辑资料，只改变一个角色关联 |
| G04异常日志 | 复用C08或M07的同一次失败，不额外制造故障 | 记录请求入口、操作者和T3_FAULT标记，关联操作日志 |

两处方法在基线都有@Transactional。异常必须从代理调用的事务方法向外传播，且标记txActive=true；若为false，本次场景无效，不能判回滚通过。这是人为注入的练习故障，不是若依自然发生的缺陷。

### 前后核验与恢复

1. 用另一只读连接保存目标sys_user的user_id、user_name、dept_id、status、del_flag，以及sys_user_role和sys_user_post的目标关联；不查询密码字段。
2. 开关关闭时先证明隔离副本同类正常请求可成功。为故障请求换唯一账号或恢复编辑基线，再开启指定故障开关并重启隔离副本。
3. 提交请求，确认异常标记和事务内位置。响应失败后重新查询：新增目标应不存在，异常中userId的角色/岗位关联为空；编辑目标资料及关联应与本轮操作前完全一致。序列号有间隙不算未回滚。
4. G04-03期望异常到达LogAspect.doAfterThrowing，操作日志status为FAIL并带可关联错误信息。没有日志时按日志观察方案调查，不用普通return error替代异常。
5. 留证后关闭开关，移除补丁并用未注入版本重建/重启隔离副本；同条件正常对照应成功。清理本轮专用对象，保存恢复查询。原ruoyi_t2_lab、原源码和共享Redis全程不改。

## IP黑名单对照

对应：TC-L11-01/02，E03、RK03。只验证登录入口按其实际获取的来源地址进行匹配，不宣称网络防火墙或代理防伪通过。

| 项目 | 设计 |
|---|---|
| 目标 | 直接访问127.0.0.1:8080，避开Vite代理改变来源；不用伪造X-Forwarded-For作为真实来源证明 |
| 获准来源 | 本机客户端显式绑定127.0.0.1；admin管理及备用登录通道也保持该来源 |
| 受限来源 | 第二客户端显式绑定127.0.0.2；黑名单只配置精确值127.0.0.2，不使用127.*或整段规则 |
| 客户端方式 | 标准HTTP客户端绑定本地源地址，例如Python http.client.HTTPConnection('127.0.0.1',8080,source_address=('127.0.0.2',0))；获准组改为127.0.0.1 |
| 预检查 | 黑名单变更前两来源均以专用账号、新有效验证码成功登录；通过本轮登录日志确认服务器看到的IP恰为各自来源。若当前Windows无法绑定127.0.0.2，或代理使两来源相同，则该执行批次阻塞，不冒充已构造 |
| 保存基线 | admin记录参数sys.login.blackIPList原值及configId，保留已登录管理会话；验证码/账号状态/失败计数均有效 |
| 设置 | 用参数管理页面或PUT /system/config修改该参数，保留其他字段；回查值。SysConfigServiceImpl.updateConfig成功后更新对应配置缓存，不直接改库留下缓存差异 |
| 对照 | 来源127.0.0.2＋正确凭据＋新有效码应拒绝；127.0.0.1同条件应成功。分别记录实际来源、时间、HTTP及业务响应、登录日志 |
| 恢复 | 从127.0.0.1管理通道恢复原参数并回查，再用两来源按原规则复验；不简单认定原值必为空 |

若管理API会话失效，使用仍未被本例黑名单覆盖的127.0.0.1重新正常登录后恢复。若实际来源与设计不符，先停止变更并排查来源，不能扩大黑名单碰运气。IpUtils.getIpAddr在无代理头时使用request.getRemoteAddr，设计因此要求直接连接且不附来源代理头。

## 验证码的过期与复用

对应：TC-L06-01/L07-01，E02、RK03。只读观察准确的captcha_codes:<uuid>，不读取或输出缓存中的验证码答案，不删除缓存制造“自然过期”。

### 过期码

1. 专用正常账号、正确密码、未锁定、来源获准。获取验证码C1，用户正常识别图像；本地保留uuid及对应输入，证据只使用代号C1。
2. 用Redis只读身份查本次键的EXISTS和PTTL，先确认存在且剩余时间为正。记录取码时间与PTTL；不把浏览器收到图片的时刻当作写入时间。
3. 等其自然到期，确认EXISTS=0、PTTL=-2，再提交原uuid和原正确答案。即使页面自动刷新，也要核对最终请求确实使用C1；必要时仅重放该专用账号的合法本地请求。
4. 应因验证码过期拒绝；再取C2，用正确凭据成功登录作对照。账号异常或网络失败不算过期校验通过。

### 已消耗码

1. 取C1并确认PTTL为正；用正常账号、合规但错误的密码、正确C1提交。
2. 确认响应已进入密码错误分支，随后检查C1键不存在。记录第一次提交仍在原TTL内，排除自然过期。
3. 立即用原C1和正确密码再次提交，应因原码已消耗拒绝；换C2正常登录。两次不得混入账号锁定。

SysLoginService.validateCaptcha先取缓存，再删除，再比较验证码；登录总流程在密码认证之前调用此方法。PTTL=-1表示键无到期时间，需要记录偏差；不能当作有效TTL边界。

## 密码失败次数与自然恢复

对应：TC-L10-01—03，E03、RK03。使用独立U锁（例如t3_lock_1010，创建前查重），普通查询权限足够，不能用admin或甲乙丙反复试错。

执行前核对启动配置中maxRetryCount=N、lockTime=T，记录覆盖来源，并用实际计数行为交叉核验。默认N=5、T=10分钟；若生效值不同按实际取值，不改业务预期去迎合默认值。

| 观察点 | 数据与步骤 | 预期 |
|---|---|---|
| 初始 | 只读GET/PTTL pwd_err_cnt:<U锁>，没有键或自然过期；否则等待或另用专用账号 | 不把未知历史次数当0 |
| N−1 | 每次用新有效验证码和合规错误密码，确认都进入密码错误分支，累计到N−1；再用正确密码和新有效码登录 | 未达阈值时认证成功，计数键消失 |
| N | 从新的干净计数开始，完成N次真实密码不匹配，核对计数为N且TTL为正；马上用正确密码和新有效码登录 | 已有计数≥N时拒绝；第N次密码错误响应不必等于后续的锁定响应 |
| 锁定期间 | 在一次拒绝前后读取PTTL并记录时间差 | 该锁定拒绝路径不应重置为完整T；只记录容许网络耗时，不伪造精确秒数 |
| 自然恢复 | 自最后一次计数递增写入开始等待PTTL=-2；不DEL、不重启Redis；用正确密码和新有效码登录 | 可重新认证，核对身份正确 |

只读命令在用户现有Redis客户端中执行，凭据本地交互输入。仅查目标计数键，不扫描或输出其他登录会话。结束后让计数自然恢复，以正确密码新登录回查；记录专用账号处置，不清共享Redis。

## 日志窗口与证据记录

本轮建议采用W_LOG=30秒、每2秒查询一次作为测试观察窗口，并记录实际采用值；这只是测试节奏，不是产品日志SLA。窗口结束仍无记录，检查查询权限、时间/时区、筛选及异步入库后再分类。

使用[T3逐例执行计划与记录模板](../T3逐例执行计划与记录模板.xlsx)逐TC填写：实际版本与配置差异、批次/时间、执行人和登录身份、实际对象/参数、检查层次、结果、状态、证据、问题、恢复及复测。参数化每个值和每次重跑追加独立记录；不覆盖首次失败。当前模板全部为未执行。

## 设计与执行的分界

以上补齐的是方法、输入、观察对象和恢复路径，可用于T3.2设计验收。账号110初始密码可用已有用户证据；5位密码登录、故障环境、双来源、计数与TTL观察均没有被本文件写成已经执行。进入各执行批次时检查条件，不满足则记该批阻塞并补救，不删除原用例、不跳过T3原定必需层次。
