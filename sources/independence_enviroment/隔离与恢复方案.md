# T5.5 隔离环境与恢复方案

准备日期：2026-10-28。此文为执行准入和恢复方案，不是测试通过记录。

## 独立边界

| 资源 | 隔离安排 | 共用环境 |
|---|---|---|
| 后端源码 | 本目录backend，来自固定提交13db1fcef36bee9ce45d2d636a1d4e8f5ed5bbc3的独立导出 | sources/backend不修改 |
| HTTP | 仅本机127.0.0.1:18080 | 8080保持原服务 |
| 数据库 | 本机新库ruoyi_t3_fault_lab；独立应用账号仅授予该库DML权限 | ruoyi_t2_lab不初始化、不注入故障 |
| Redis | 拟在已有Linux启动独立进程16379，经SSH转发到本机16379；独立密码，不持久化 | 原Linux6379进程、配置和数据不改 |
| 文件 | .private保存凭据，logs保存私有日志，uploads保存隔离上传，artifacts保存构建产物 | 不复用共用日志或上传目录 |

不克隆整个Linux系统。独立Redis复用已安装程序，但使用不同进程、端口、密码和内存数据。计划由SSH前台进程运行，Redis日志回收至本目录；不在Linux落持久化数据库文件。该方案须先取得SSH访问、核实端口和程序才能落实。

## 执行准入

1. 同名测试库、应用账号、隔离源码目录若已存在，停止自动创建并确认用途，不覆盖未知资源。
2. 记录共享业务配置摘要、原后端源码和构建产物摘要；导出源码，不复制共用私有配置。
3. 仅在确认新建的专用库中执行固定初始化脚本；独立应用账号没有读取或写入ruoyi_t2_lab的权限。
4. 核对独立Redis的run_id、端口、认证与连接通路；原共享Redis仍可用且run_id保持一致。
5. 先构建未注入版本，启动18080，记录命令与实际连接目标，验证正常创建、查询、修改和日志链。
6. 正常对照成功后才在独立源码加入精确用户名和启动属性双重保护的故障点。

## 故障点

- TC-C08-01：insertUser完成用户、岗位、角色写入后，返回前触发insert-after-all；仅匹配t3_fault_new。
- TC-M07-02：updateUser完成用户更新及关联替换后触发update-after-all；仅匹配t3_fault_edit，编辑请求只改变角色关联。
- TC-G04-03：复用上述同次异常，核对到达LogAspect.doAfterThrowing、操作日志FAIL和业务回滚，分别判定。

需要真实异常标记txActive=true。普通参数拒绝、普通return error或客户端ROLLBACK不能替代这三个用例。若缺少隔离、正常对照或可靠触发证据，对应项目如实保留未执行/阻塞，不能写通过。

## 数据和恢复

- 记录新库中实际生成的部门、角色、用户和岗位ID，不套用共用库的基线ID。
- 测试前保存本批对象基础字段、用户角色、用户岗位快照；写后使用独立读取连接比较。
- 变更及旧会话验证只针对本批隔离对象，保留原始失败并关联原缺陷编号，不要求产品全绿。
- 异常后先留存证据，再关闭故障开关；将实验源码恢复至固定基线并构建未注入版本，完成正常恢复对照。
- 正常业务创建的用户通过正常删除接口清理；退出本批会话，保留审计和逻辑删除历史。
- 保留测试库和隔离资料供复查，不自动DROP整个库；账号仅保留该库权限。结束后可停止本批18080进程及独立Redis/SSH进程，绝不根据名字批量停止Java、Redis或SSH。
- 需要停止时，先核对清单中的PID、命令行、端口、Redis run_id及目标库。独立Redis用认证后的SHUTDOWN NOSAVE收尾，不清理共用Redis。
- SSH、数据库和临时账号口令不进入Markdown、SQL交付、请求集合或Git。私有原始日志留在.private/logs边界内，公开证据使用字段白名单。
